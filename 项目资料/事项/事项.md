# my_racecar（复件）运动数据与 `/encoder` 来源

最近修改日期：2026-09-27。

## `/encoder` 在哪里发布？

**当前提供的源码中没有找到 `/encoder` 的发布节点。** 下面是源码能确认的关系：

| 文件或节点 | 对 `/encoder` 的作用 | 实际输出或用途 |
| --- | --- | --- |
| `my_racecar（复件）/src/get_distance.cpp` | 订阅 `nav_msgs/msg/Odometry` 类型的 `encoder`。 | 读取 `twist.twist.linear.x`，积分后发布累计路程 `/distance`。 |
| `智能车/智能车/智能车/encoder_imu/src/imu_encoder_mix.cpp` | 订阅 `/encoder`，同时订阅 `/IMU_data`。 | 用编码器速度和 IMU 姿态计算并发布 `/encoder_imu_odom`；它**不发布 `/encoder`**。 |
| `my_racecar（复件）/src/pure_track_test.cpp`、`transform_v.cpp` | 均订阅 `encoder`。 | 读取当前速度用于路径跟踪或速度控制。 |
| `my_racecar（复件）/launch/save_path.launch.py` | 启动 `get_distance`、`imu_encoder_mix`、`save_path`。 | 启动的是 `/encoder` 的使用者，没有在该文件中启动其发布者。 |

上述检查覆盖当前提供的智能车项目源码，**不能据此断定车上没有 `/encoder`**。它可能由车上另行安装或开机启动的底盘驱动发布；目前没有该驱动的源码或车上实时节点信息，不能确定发布者名称、硬件接口或速度单位。

在**小车终端**、加载实际 ROS 2 环境后查发布者：

```bash
ros2 topic info /encoder -v
ros2 topic echo /encoder --once
```

`ros2 topic info /encoder -v` 的 `Publishers` 会列出当前实际发布节点及消息类型；若发布者数为 0，则当前运行环境没有节点在发布它。拿到节点全名后，可用 `ros2 node info /节点全名` 查看其接口，再查该节点所属的车载驱动包或开机服务。`echo` 能收到消息只说明有数据，还要核对 `twist.twist.linear.x` 的单位、方向和时间戳，才能判断是否可用于距离积分。

## 这些数据怎样用于录制路径？

```text
车载外部节点发布 /encoder
    ├─ get_distance.cpp：速度积分 → /distance
    │      └─ save_path.cpp：每累计达到 save_dx（启动文件设为 0.1）时触发存点
    └─ imu_encoder_mix.cpp：结合 /IMU_data → /encoder_imu_odom
           └─ save_path.cpp：取 x、y、yaw 写入 include/path.csv
```

`get_distance.cpp` 的 `/distance` 是**累计行驶路程**，不是小车在地图中的位置；`save_path.cpp` 用它决定**何时保存**，保存的位姿另来自 `/encoder_imu_odom`。路径录制文件还订阅 `/scan` 保存起点参考扫描。`get_distance.cpp` 中已补充逐行中文注释，计算语句未更改。

## 2026-09-26：`get_distance` 的时间差与异常时间处理

`my_racecar（复件）/src/get_distance.cpp` 的 `encoder_callback()` 每收到一条 `/encoder`，先用 `this->now()` 取得**回调执行时的节点时间**，再计算 `dt = (current_time - last_time).seconds()`。它**没有读取** `/encoder` 消息的 `header.stamp`。正常积分为 `本段路程 = [上一帧速度绝对值 + 当前帧速度绝对值] / 2 × dt`，并把本段路程加入 `distance`；发布到 `/distance` 前再乘 `distance_k`（默认 1）。因为使用速度绝对值，倒车同样增加累计路程。

| 收到 `/encoder` 时的情况 | 代码处理 | 对 `/distance` 的影响 |
| --- | --- | --- |
| 第一条消息 | 记录当前速度和时间，清除 `first_message`，直接返回。 | 不累计、不发布，避免把启动前的时间算入。 |
| `0 < dt ≤ 1` 秒 | 用相邻两帧速度平均值乘 `dt`，更新累计路程并发布。 | `/distance` 增加；速度与时间单位正确时，得到该段估计路程。 |
| `dt ≤ 0` 或 `dt > 1` 秒 | 打印 `Abnormal time interval`，把当前速度和时间设为新的起点，直接返回。 | 跳过整段，不累计也不发布；下一条正常消息再继续。 |

异常分支能防止一次时钟跳变或长间隔产生巨大的错误积分，**不能补回跳过期间的真实行驶路程**。例如车辆保持约 1 m/s，但两次回调间隔 2 秒，代码会跳过这段；若车确实一直在行驶，累计路程约少计 2 米。这个数字只是按恒速作的示例，真实误差取决于断流期间的运动。`distance_k` 是整体比例系数，不能修复这种漏计。

这会影响路径录制：`save_path.cpp` 的 `dis_callback()` 仅在 `dis - last_dis >= save_dx` 时写入当前 `x/y/yaw`，`save_path.launch.py` 将 `save_dx` 设为 `0.1`。若 `/distance` 因异常间隔少计，按路程触发的路径点可能漏掉或与实际行驶位置不均匀。`save_path.cpp` 还从另一个订阅 `/encoder_imu_odom` 取最近位姿，并未按时间戳把距离消息和位姿消息精确配对；因此也要关注两路消息的延迟。

在**小车终端**检查：

```bash
ros2 topic info /encoder -v
ros2 topic hz /encoder
ros2 topic echo /encoder --once
ros2 topic hz /distance
```

先确认 `/encoder` 有发布者、消息类型为 `nav_msgs/msg/Odometry`，发布频率持续稳定，并观察 `get_distance` 终端是否反复报 `Abnormal time interval`。`ros2 topic hz` 反映收到消息的频率，不能证明消息头时间戳准确；当前代码的 `dt` 用的是节点时钟。若反复出现异常，先查编码器驱动是否断流、车载时钟或 ROS 仿真时间是否跳变，以及节点是否长时间未处理回调。修复并重新录制、检查 `path.csv` 的相邻点间距后，再使用这条路线。

### 2026-09-26 补充：`this->now()` 用谁的时间，会不会引入误差？

**会。** `this->now()` 取得的是 `get_distance` 节点自己的 ROS 2 时钟，而不是编码器的硬件时钟。按 [ROS 2 时钟设计说明](https://design.ros2.org/articles/clock_and_time.html)，节点未启用 `use_sim_time` 时，ROS 时间与车载机系统时间一致；启用后由 `/clock` 提供时间。当前 `save_path.launch.py` 没有显式设置 `get_distance` 的 `use_sim_time`，但车上最终参数值仍应现场查询：

```bash
ros2 param get /get_distance use_sim_time
ros2 topic echo /encoder --once
```

`get_distance.cpp` 在**回调执行时**打时间，所以算的是两次消息处理的间隔。编码器实际采样后还要经过驱动发布、ROS 2 传输和回调排队；若每帧延迟始终相同，延迟在相减时大致抵消，若延迟变化，`dt` 就偏离真实采样间隔。车载系统时间被校时或仿真 `/clock` 跳变时，也可能触发异常时间分支。`ros2 topic hz /encoder` 可检查到达频率，却不能证明采样时间准确。

| 算时间差的依据 | 能反映什么 | 仍需注意什么 |
| --- | --- | --- |
| 当前代码的 `this->now()` | 节点处理相邻消息的时间间隔。 | 受传输、排队抖动及当前时钟跳变影响。 |
| `/encoder.header.stamp` | 若由驱动在**实际采样时**填写，可反映相邻采样间隔。 | 必须先确认时间戳非零、单调且采样时钟一致；若驱动在发送时才填写，不能自动解决误差。 |
| 单调时钟计算回调间隔 | 不受系统时钟拨动影响。 | 仍然算的是回调间隔，不能消除传输和排队抖动。 |

因此，不能仅凭“ROS 2 提供的时间”就认定距离积分准确，也不要未经核对便把代码改为使用 `header.stamp`。先找到车上 `/encoder` 的实际发布驱动，确认它如何填写时间戳，再决定是否改为按消息采样时间积分。当前只有静态源码，没有车上时间戳和频率记录，无法给出本车的实际误差大小。

## 2026-09-26：`save_path.cpp` 保存的 `x、y、yaw` 是哪里的？

这三个值来自 **`/encoder_imu_odom` 的车体位姿**，不是 `/distance`，也不是雷达扫描中的点。`encoder_imu/src/imu_encoder_mix.cpp` 用 `/encoder` 的线速度 `v` 和 IMU 姿态的航向 `theta` 计算 `vx = v × cos(theta)`、`vy = v × sin(theta)`，再对时间积分得到 `x、y`；它把收到的第一帧 IMU yaw 记为 `theta_first`，发布时使用 `theta = 当前 IMU yaw - theta_first`。消息声明 `header.frame_id = odom`、`child_frame_id = base_footprint`，因此按该消息的定义，它表达的是 **`base_footprint` 相对 `odom` 的平面位姿**。

| `path.csv` 字段 | `save_path.cpp` 的来源 | 含义 |
| --- | --- | --- |
| `x` | `/encoder_imu_odom.pose.pose.position.x` | 车体参考点在 `odom` 坐标系下的 x。 |
| `y` | `/encoder_imu_odom.pose.pose.position.y` | 车体参考点在 `odom` 坐标系下的 y。 |
| `yaw` | `/encoder_imu_odom.pose.pose.orientation` 四元数提取 | 车体在 `odom` 坐标系下的航向角，保存为弧度。 |

`save_path.cpp` 的 `odom_callback()` 只是把最新的 x、y、yaw 保存在节点变量中；`dis_callback()` 收到 `/distance` 且 `dis - last_dis >= save_dx` 时，才把**最近一次收到的**位姿写入 `/home/racecar/src/my_racecar/include/path.csv`，并发布显示点。因此 `/distance` 决定“何时存”，`/encoder_imu_odom` 决定“存什么坐标”；两路消息没有按时间戳严格同步。`odom` 零点随里程计启动而定，源码也没有给出 `base_footprint` 在实物车体上的确切机械位置，所以不能把 CSV 数值直接说成赛场固定地图坐标。

**可视化坐标系有一处不一致：**`show_point()` 直接把上述 `odom` 数值赋给 Marker 的位置，却写了 `marker.header.frame_id = "map"`，没有执行 `odom → map` 变换。Marker 在 RViz 中被当作 `map` 坐标显示，不足以证明 CSV 已变为地图坐标；若 `map` 与 `odom` 不重合，显示点会偏移。本条只解释当前源码，没有改动车辆的原有控制和坐标计算。

### 2026-09-26 补充：是否就是从出发点开始的位移？

**设计含义上是本次里程计启动后的相对位移，而不是赛场上一个固定点的绝对坐标。** `imu_encoder_mix.cpp` 把 `x、y` 初始设为 0、把首帧 IMU yaw 作为航向零点，之后对 `v × cos(theta)`、`v × sin(theta)` 积分。因此小车每次重新放置并重启此节点，数值按本次启动重新计算；如果节点未重启，手动搬动车辆也不会让里程计自动识别新的赛场起点。

但**当前实现不能保证第一条 `/encoder_imu_odom` 的 `x、y` 真从 0 开始**：全局 `last_time` 没有在首次回调前设为当前时间；首次回调把 `flag` 改为 `false` 后，紧接着仍进入积分分支，用 `当前时间 - 默认零时间` 算第一段 `dt`。若首帧编码器速度非零，可能产生异常大的第一段位移。`mapping/scripts/odom_tf_adapter` 为建图 TF 记录并减去首个有效位姿，但只修正它发布的 `odom → base_footprint`，**不会改写原 `/encoder_imu_odom` 或 `save_path.cpp` 写入的 `path.csv`**。所以在实车录路径前，应静止启动车辆节点，并检查 `/encoder_imu_odom` 首帧及 `path.csv` 前几行，不能仅凭坐标帧名认定起点就是 `(0,0)`。

## 2026-09-27：`move_new.launch.py` 和 `move_test.launch.py` 有什么区别？

文件名里的 `new`、`test` 只是命名，**不能据此判定哪个较新或哪个已投入使用**。应以实际启动节点、参数在源码中是否被读取，以及上层 launch 的包含关系判断。

| 对比项 | `launch/move_new.launch.py` | `launch/move_test.launch.py` |
| --- | --- | --- |
| 启动节点 | `map_recieve_node`、`get_local_path`、`pure_track_test`。 | `imu_encoder_mix`（默认启用）、`get_local_path`、`pure_track_test`。 |
| 里程计 | 不启动 `imu_encoder_mix`；`get_local_path` 仍需要外部提供 `/encoder_imu_odom`。 | 默认启动 `encoder_imu` 包的 `imu_encoder_mix`；建图组合入口传 `start_odom=false`，由外层启动一次。 |

| 路线配置 | `stop_point=4`、`slow_point=20`；未设置 `start_icp`，`get_local_path` 使用默认值 0。 | `stop_point=3`、`slow_point=15`、`start_icp=1`、`pub_global_path=0`。 |
| 跟踪配置 | `linear_x=0.6`、`v_mode=1`（匀速）、停车点索引 180/510。 | `linear_x=1.5`、`v_mode=0`（按路径速度）、前馈索引 12、红绿灯索引 101、停车点索引 18/229。 |
| 当前建图入口 | `race_mapping.launch.py` 没有包含它。 | `race_mapping.launch.py` 在建图就绪检查通过后明确包含它。 |

**`move_new` 不等于“已经集成 YOLO”。** 该文件把 `light_mode=0` 注释为“基于 yolo 自动停车”，但当前 `src/pure_track_test.cpp` 没有声明或读取 `light_mode`，也没有相机或 YOLO 推理节点；`traffic_light_area` 同样没有在这个控制器中声明或读取。`src/pure_track_test.cpp` 实际订阅的是 `std_msgs/msg/Int32` 类型的 `traffic_light` 话题：路径索引达到 `traffic_light_index` 后进入等待，收到值 1 时解除等待，或由 `traffic_light_time` 定时器解除。**谁识别红绿灯并发布该话题，在本包中未找到。** `move_new` 未设置 `traffic_light_index`，控制器默认值为 0，因此其红绿灯等待条件可能在第一个非空局部路径上就满足；需实车核对。

`move_new` 还传入 `ab_flag=2`、`concat_dy=0.0`，但当前 `src/get_local_path.cpp` 只保留这两个成员/旧注释，没有把它们声明并读取为 ROS 参数；这两个传参不构成已经启用的路线拼接功能。当前建图流程选择 `move_test` 是 `race_mapping.launch.py` 的显式代码决定，同时保留了旧固定路线控制参数；**不能仅因为文件名含 `new` 就改用 `move_new`**，两套入口的依赖和行驶参数不同。以上是本地源码结论，车上实际启动的是哪一套，还应检查运行命令和节点。

## 2026-09-27：`get_local_path.cpp` 是否要求小车在原点启动？

**节点没有“只有在原点才能启动”的判断。** 它启动时读取 `/home/racecar/src/my_racecar/include/path.csv`；收到 `/encoder_imu_odom` 后，用当前 x/y/yaw 在 CSV 路线中找附近的点，转换到车体局部坐标并发布 `/my_local_path`。`pub_global_path=0` 只是不发布 `/my_global_path` 和 `/my_current_path`，不能据此判断 CSV 没读到。当前副本的 CSV 首个数据点约为 `(0.105, -0.0016)`，不是严格的 `(0,0)`，但这条路线整体使用录制时的里程计坐标。

| 起步情况 | 当前源码的行为 | 是否适合直接沿原路线行驶 |
| --- | --- | --- |
| 车放回录制路线的起点附近，并重新建立相近的里程计零点/车头方向 | 路线坐标和当前里程计坐标有机会对齐；`move_test` 设置 `start_icp=1`，尝试用 `init_scan.csv` 与当前 `/scan` 求起点偏移。 | 还需检查 ICP 结果、局部路径与实际路线是否对齐。 |
| 方框内略有位置或朝向偏差 | ICP 可以尝试局部匹配，但当前实现从零偏移开始、对应点距离上限为 0.4 m，成功还要求收敛及误差阈值；不能保证每次都校正。 | 只在实测匹配可靠、起点与路径对齐时使用。 |
| 车放到路线中途或远离原起点 | 节点仍会运行；它没有对任意起点做全局重定位，也没有“离路线太远就不发布局部路径”的距离门槛。 | 不能因为 `/my_local_path` 有数据就认定可安全起跑。 |

`get_local_path.cpp` 的 `odom_callback()` 对原始里程计应用 ICP 保存的 `dx/dy/dyaw` 后找最近路径点；**即使 ICP 尚未成功，回调也没有以 `calibration_done_` 为条件阻止局部路径发布**，此时修正量仍为初始零值。另需注意 `imu_encoder_mix.cpp` 首帧时间未初始化可能产生异常大的原始 x/y，见上节。建图入口的起跑检查与固定路线坐标是否正确对齐是两个要分别核实的问题。操作上应从已录制路线的起点区域静止启动，核对 `/encoder_imu_odom` 首帧、ICP 日志、`/my_local_path` 和实际路线位置后再放车；此处不是“必须恰好物理坐标 `(0,0)`”的要求。

## 2026-09-27：雷达只测障碍物距离时，需不需要外参？

先纠正本项目实际用途：当前 `move_test.launch.py` 没有启动单独的障碍物检测节点。它启动的 `get_local_path.cpp` 在 `start_icp=1` 时，使用**整帧 `/scan` 的距离和角度**算雷达坐标系中的二维扫描点，与起点参考 `init_scan.csv` 做 ICP，得到 `dx/dy/dyaw`，随后把这三个数用于修正 `/encoder_imu_odom` 的 x/y/yaw，再选取 `path.csv` 附近的路线点。它不是只取一个“障碍物距离”传给底盘。

| 实际用途 | 是否需要雷达到车体的位置/角度外参 | 当前项目情况 |
| --- | --- | --- |
| 只在雷达自身坐标系中判断“前方距离是否小于阈值”并停车 | 单纯距离阈值不一定需要 x/y/z；但必须明确雷达哪一角度对应车头、雷达与车体外廓的偏移。 | 这不能代表当前 `get_local_path` 的扫描匹配。 |
| 用当前扫描与同一雷达的起点参考扫描做 ICP | 两帧扫描在同一雷达坐标定义下可尝试匹配，不一定先发布车体 TF。**把匹配出的平移/转角用作车体位姿校正时，必须考虑雷达相对车体的方向和位置，尤其是转弯时的安装偏移。** | 旧 `get_local_path.cpp` 没有读取雷达 TF，也没有雷达外参参数，却直接把 ICP 的 `dx/dy/dyaw` 用于车体里程计修正；这隐含雷达坐标与车体坐标足够一致的假设，不能认定几何校正准确。只增加静态 TF 不会自动改变它的计算。 |
| 用 SLAM Toolbox 把 `/scan` 与里程计结合建图 | **需要** `base_footprint → 雷达帧` 的正确外参，才能把扫描放进车体/地图坐标链。 | 新增 `mapping/launch/race_mapping.launch.py` 要求实测 `laser_x/y/z/yaw`，漏填会拒绝启动，并由静态 TF 节点发布该变换。 |

因此，“只检测一个距离”的简化场景不能推出“本项目不用雷达外参”。对于当前比赛建图入口，仍应量雷达扫描原点到车体参考点的 x/y/z 和相对车头的 yaw，按 `mapping/README.md` 提供；旧 ICP 若要作为精确的车体位姿校正，还需核对或修改其雷达到车体的坐标转换。上述是源码分析，安装外参和校正误差需实车验证。

## 2026-09-27：建图只求粗略效果，能否断开雷达 TF 后边走边建？

**不能在现有 `race_mapping.launch.py` + SLAM Toolbox 链路中直接断开。** 小车移动时，建图程序必须知道每一帧扫描相对车体/里程计坐标的位置，才能把不同时刻的障碍点放到同一张地图。当前链路是 `odom → base_footprint → 雷达帧`，SLAM Toolbox 再发布 `map → odom`。本包的 `mapping_ready` 还会按扫描时间戳查询 `map → 雷达帧` 和 `map → base_footprint`；查不到就不能通过起跑检查，固定路线控制不会被放行。SLAM Toolbox 的[项目说明](https://github.com/SteveMacenski/slam_toolbox)也把扫描输入和有效的里程计到车体 TF 列为运行接口。

| 做法 | 是否可用于当前边走边建图入口 | 实际含义 |
| --- | --- | --- |
| `publish_laser_tf=false`，但没有别的节点发布雷达 TF | **不可以**。起跑检查无法查询完整变换，SLAM Toolbox 也无法可靠放置扫描。 | 这是断链，不是“放宽精度”。 |
| `publish_laser_tf=false`，已有其他节点发布正确的 `base_footprint → 雷达帧` | 可以保持链路完整，但必须避免重复发布同一 TF。 | 只是换发布者，仍需外参。 |
| 用粗略/零外参保持 TF 连通 | 技术上可能处理扫描并生成一张地图，但车体与雷达的真实偏移会被忽略，地图位置、转弯和后续定位可能出错；通过检查也不等于地图可用。 | 这是“错误外参下的建图”，不能保证完成比赛路线。 |
| 不用 SLAM Toolbox，另写程序按里程计和雷达数据绘制栅格或播放预制地图 | 可以做可视化演示，但不属于当前真实 SLAM 建图链路。 | 需要另一套实现，不能把它当成当前方案的存图和重定位结果。 |

因此，若只想降低测量精度要求，可以先实测一个近似安装位置并保持 TF 连通，再观察地图质量；**不能把雷达 TF 完全断开，同时指望当前 SLAM Toolbox 在车移动时正常建图**。`mapping/launch/race_mapping.launch.py` 中 `publish_laser_tf=false` 的注释也写明其用途是“外部 TF 已发布”。
