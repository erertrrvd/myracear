# YOLOv5n 电脑分布式通信：运行指令（详细版）

> 简版见同目录 `指令集.md`。本文的 `remote_vision_bridge.py` MD5 已更新为带 `--enable-control` 的新版；其余内容中“没有修改项目里任何原有文件”指视觉文件，运动代码 `pure_track_test` 的改动不属于这里。

小车只负责拍摄并把画面传给电脑，**电脑**用 YOLOv5n 识别，结果传回小车，由小车发布 ROS 话题。小车上不再需要跑 NPU、conda、torch，系统压力小很多。

## 1. 这个文件夹里有什么

**没有修改项目里任何原有文件。** 这里全部是新增的文件，另有两个原项目文件的原样副本，方便在这个文件夹里直接运行电脑端。

| 文件 | 放在哪 | 作用 |
|---|---|---|
| `remote_vision_bridge.py` | **小车** | 采集摄像头、JPEG 编码、TCP 服务端、发布话题、看门狗 |
| `start_remote_vision.sh` | **小车** | 小车端启动入口（检查摄像头占用，用 `/usr/bin/python3` 启动） |
| `remote_proto.py` | **小车和电脑** | 通信协议（只用标准库） |
| `pc_vision_client.py` | **电脑** | 连小车收画面、识别、把结果传回，本机窗口显示 |
| `start_pc_vision.ps1` | **电脑** | 电脑端启动入口（先检查端口通不通） |
| `light_infer.py`、`det_utils.py` | **电脑** | 原项目 `camera_capture/` 里的原样副本，电脑端复用其中的识别和判断逻辑；**小车端不需要** |
| `light_listener.py` | 小车 | 订阅并打印话题（看结果用） |
| `README_远程视觉.md` | — | 原理和行为的补充说明 |

项目里的位置：这些文件在仓库的 `camera_capture/` 里也有同样的一份（`light_infer.py`、`det_utils.py` 本来就在那里）。

## 2. 原理

```
小车 /usr/bin/python3                                  Windows 电脑 D:\light_ai\venv
  remote_vision_bridge.py                                pc_vision_client.py
    摄像头 → JPEG                                           连小车 192.168.5.100:9000
    TCP 服务端 :9000 ──只发最新一帧────────────▶            收帧 → YOLOv5n(onnxruntime)
                    ◀────识别结果（JSON）───────             → 判断 red/green/off/none/conflict
    发布 /traffic_state、/traffic_light_box                 本机窗口显示画面和框
    0.5 秒没结果 → stale
```

- 小车当服务端监听，电脑主动连，Windows 防火墙不会拦。
- 小车永远只发最新一帧；电脑处理不过来时跳过中间帧，不排队。
- 延迟用小车自己的时钟算，不比较两台机器的时间（小车时钟不准）。
- **只有 `green` 才算放行**；没有电脑连接、结果过期、状态不明都是 `stale`/不放行。
- 话题和原来车上识别发布的完全一样：`/traffic_state`、`/traffic_light_box`。`/traffic_light` 验证阶段仍然关闭，不影响小车运动。

| 电脑 | `D:\light_ai\venv` 里有 `onnxruntime`、`torch`、`opencv`（已装好） |

## 7. 第 3 步：看结果

**电脑上**会弹出窗口：摄像头画面、框、左上角状态和 `GO`/`STOP`，窗口里按 `q` 退出。终端每 5 秒打印一行识别帧率、单帧耗时、跳过帧数。

**小车上**每 5 秒打印一行：采集帧率、编码耗时、发送帧率和码率、收到结果的速率、往返延迟 p50/p95；状态变化时打印一行。

**话题**（小车另开终端）：

```bash
source /opt/ros/humble/setup.bash
ros2 topic echo /traffic_state
ros2 topic echo /traffic_light_box
ros2 topic hz /traffic_state
/usr/bin/python3 /home/racecar/src/my_racecar/camera_capture/light_listener.py
```

| 话题 | 类型 | 内容 |
|---|---|---|
| `/traffic_state` | `std_msgs/String` | `red` / `green` / `off` / `none` / `conflict` / `stale` |
| `/traffic_light_box` | `std_msgs/Float32MultiArray` | `[x1,y1,x2,y2,灯箱置信度,亮灯置信度,图宽,图高,结果延迟秒,识别fps]`，没灯箱时框为 -1 |

状态含义：`red` 灯箱里有亮红灯；`green` 有亮绿灯；`off` 有灯箱没亮灯；`none` 没看到灯箱；`conflict` 红绿同时亮；`stale` 没有电脑连接或结果过期（超过 0.5 秒）。**只有 `green` 才算放行。**

## 8. 参数

小车端（接在 `bash start_remote_vision.sh` 后面）：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--fps` | 15 | 发给电脑的帧率上限；负载太高就降到 10 |
| `--quality` | 80 | JPEG 质量；降到 70 可省带宽 |
| `--width` `--height` | 640 480 | 画面大小；模型输入是 640×640 的 letterbox，缩小会降低精度 |
| `--port` | 9000 | 监听端口（电脑端要一致） |
| `--enable-control` | 关 | 接入运动控制：订阅 `/traffic_light_req`，请求期间发布 `/traffic_light`；默认只发验证话题 |
| `--stale-sec` | 0.5 | 结果距拍摄超过这么久就当作 `stale` |
| `--rate` | 20 | 话题发布频率 |
| `--selftest` | 关 | 只测采集和编码负载，不连电脑 |
| 环境变量 `BIND` | 0.0.0.0 | 监听地址，建议设成 `192.168.5.100` |

电脑端（`start_pc_vision.ps1` 支持 `-Car`、`-Port`、`-NoShow`；更多参数用直接命令）：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--car` | 192.168.5.100 | 小车 IP |
| `--port` | 9000 | 端口 |
| `--model` | 视觉模型 `yolov5n_best.onnx` | 换模型文件 |
| `--conf-box` `--conf-lamp` | 0.5 0.5 | 灯箱、亮灯置信度阈值 |
| `--confirm` | 3 | 连续几帧一致才切换状态 |
| `--ar-min` `--ar-max` | 2.5 4.5 | 灯箱长宽比范围（过滤椅子、人） |
| `--cy-min` `--cy-max` | 0.20 0.85 | 灯箱中心高度范围 |
| `--no-filter` | 关 | 关闭几何过滤 |
| `--no-show` | 关 | 不弹窗 |

## 9. 和原来车上识别的切换

两条路互不影响（原有文件都没改），**同一时间只能开一条**，因为都要用摄像头。

| | 车上识别（原来） | 电脑识别（本文） |
|---|---|---|
| 小车 | `bash start_vision.sh` | `bash start_remote_vision.sh` |
| 电脑 | 不需要 | `start_pc_vision.ps1` |
| 小车负载 | 高（NPU 推理加 torch/NMS） | 低（只采集编码和收发） |
| 依赖 | `.om`、CANN、conda | 电脑和 WiFi 在线 |

切换前先 `Ctrl+C` 停掉正在运行的那条。`start_remote_vision.sh` 发现车上识别在运行或摄像头被占用会拒绝启动并提示。

## 10. 停止与清理

- 停止：电脑端窗口按 `q` 或终端 `Ctrl+C`；小车端 `Ctrl+C`。电脑断开后，小车端状态立即变 `stale`；电脑重新启动会**自动重连**。
- **撤掉这个功能**：不涉及 git，也没有改任何原有文件，在小车上删掉 3 个文件即可：

```bash
cd /home/racecar/src/my_racecar/camera_capture
rm -f remote_vision_bridge.py remote_proto.py start_remote_vision.sh
```

## 11. 排错

| 现象 | 可能原因 | 处理 |
|---|---|---|
| `start_remote_vision.sh` 提示摄像头被占用 | 别的程序在用 `/dev/video0` | 按提示里的进程号关掉（`record_video.py`、`start_vision.sh` 等） |
| 提示车上识别正在运行 | `light_infer.py` 在跑 | 先 `Ctrl+C` 停掉，或 `pkill -f light_infer.py` |
| `Test-NetConnection` 不通 | 小车端没启动；电脑不在 `192.168.5.x`；开了 VPN；端口不一致 | 先在小车上启动，`ping 192.168.5.100`，关 VPN |
| 电脑端一直 `连接中断或失败 ... 重试` | 小车端没在监听或被防火墙拦 | 看小车终端有没有 `等待电脑连接`，确认 IP 和端口 |
| 小车终端提示 `打不开 0` | 摄像头被占用或设备不是 `/dev/video0` | `fuser -v /dev/video0`；`ls /dev/video*` |
| 电脑窗口画面卡顿、延迟大 | WiFi 差或帧率过高 | 小车端降 `--fps 10 --quality 70`；离路由器近一些 |
| `ros2 topic echo /traffic_state` 一直是 `stale` | 电脑端没连上，或结果超时 | 看电脑端是否在运行、小车端是否显示“电脑已连接” |
| `ros2 topic echo` 提示 topic does not appear to be published yet | 小车端没启动，或没 `source /opt/ros/humble/setup.bash`，或两端 `ROS_DOMAIN_ID` 不一致（只在跨机看话题时） | 在小车本机看话题；先启动 `start_remote_vision.sh` |
| 小车端报 `No module named rclpy` | 用了 conda 的 `python3` | 用 `bash start_remote_vision.sh`，它会用 `/usr/bin/python3` |
| 电脑端找不到模型 | 默认模型路径不存在 | 用 `--model` 指定 `.onnx` 的完整路径 |
| 小车端打印 `发送中断：...` | 电脑端断开或关闭 | 正常，电脑重新启动会自动重连 |

## 12. 注意事项和还没验证的地方

- **已验证（在电脑上回环，用录好的视频当摄像头）**：小车端和电脑端能互传画面和结果，状态随画面变化（none → red → green），往返延迟约 45 到 60 ms；电脑断开后小车端立即变 `stale`；超时转 `stale`、乱序结果不覆盖新结果、非法结果被丢弃（单元测试）。
- **没有验证**：在小车上实际运行；真实 WiFi 下的延迟和丢帧；小车上的 CPU 占用；ROS 话题发布（Windows 上没有 ROS，无法测）；对着真实红绿灯、人、椅子的识别效果。
- **总延迟估计 100 到 400 ms**（WiFi 单程 25 到 170 ms 加识别约 40 ms）。车速 1 到 2 m/s 时会多滑 0.1 到 0.8 m，将来做停车控制时，停车阈值要把延迟算进去。
- 这条 TCP 端口**没有认证**，只在局域网内使用，建议 `BIND=192.168.5.100`。
- 比赛规则没有写是否允许场外计算，赛前要确认；链路断了只能退回车上的 `start_vision.sh`（`.om`），或者不放行。
- 小车性能瓶颈是推断（torch、NPU 推理、车上还在开的 rviz2），**还没量过**；改造前后建议都用 `top` 对比。
