# 红绿灯模型：YOLOv5n / YOLO11n 训练、转 .om 和验证的全过程

把我们当时怎么采集数据、怎么标注、怎么训练、怎么转成小车用的 `.om`、怎么验证的过程、指令、脚本和结果都整理在这里。**所有数字都来自当时实际跑出来的结果；没验证过的地方都标明了。**

## 0. 总览

**目标**：识别比赛红绿灯。先框出灯箱，再判断亮的是红灯还是绿灯，红灯停、绿灯走。

**流程**

```
小车摄像头录视频 → 抽帧 → 自动标注（灯箱 / 亮红灯 / 亮绿灯）→ 按视频划分并打包
→ 训练（YOLOv5n，上车用；YOLO11n，电脑上验证）→ 导出 ONNX（opset 12）→ 检查 ONNX
→ 电脑上用验证集验证 → Linux 电脑用 CANN 7.0.RC1 转 .om → 小车上加载并运行
```

**结果一览**（验证集是完全没参与训练的 3 个视频，344 张）

| 模型 | 训练位置 | 最好的一轮 | 精确率 | 召回率 | mAP50 | mAP50-95 | 用途 |
|---|---|---|---|---|---|---|---|
| YOLOv5n（三类） | 另一台有显卡的 Linux 电脑，100 轮 | 第 95 轮 | 0.999 | 1.000 | 0.995 | 0.911 | **上车用**（转成 `.om`） |
| YOLO11n（三类） | 同上，100 轮 | 第 86 轮 | 0.999 | 1.000 | 0.995 | 0.927 | 电脑上验证；**不能直接上车** |

用我们的判断逻辑（`light_infer.py`）在 344 张验证图上实测：红灯 172 张全判 `red`，绿灯 172 张全判 `green`，**错 0 张，红判绿 0**。**验证集和训练集来自同一间教室、同一块灯箱，所以分数偏高，不代表换环境也一样准。**

## 3. 标注与数据集

### 3.1 类别

| 编号 | 类别 | 含义 |
|---|---|---|
| 0 | `light_box` | 整个灯箱 |
| 1 | `red_on` | 亮着的红灯 |
| 2 | `green_on` | 亮着的绿灯 |

灯箱里三个灯从左到右是红、橙、绿，所以**按位置**判断亮的是哪个灯。橙灯没有单独作为类别（没有橙灯亮的数据）。

### 3.2 标注方法：自动生成，不是人工拉框

1. **灯箱框**：优先用我们先训练好的灯箱检测模型的结果（置信度 ≥ 0.5 且长宽比合理）；没有时用“橙灯定位”作后备：橙灯一直是橙色，容易定位，从橙灯向左右上下扩展到灯箱的深色边缘（`label.py` 的 `orange_blob`、`profile_box`）。
2. **亮灯框**：在灯箱框里找亮度很高的白色亮核，按在灯箱里的位置分类：靠左（相对位置小于 0.36）是红灯，靠右（大于 0.64）是绿灯，中间是橙灯（不标）；再检查亮核周围光晕的颜色（红灯要偏红、绿灯要偏绿）；框的大小按灯的直径来定（`label2.py` 的 `lamps`）。
3. **剔除拿不准的帧**，不放进数据集：灯箱被切在画面边缘（可能只露出半个灯）；模型只在画面上沿看到一条黑边；画面里有亮灯但没框到灯箱（不能当负样本）。
4. 灯不亮的帧，标签里只有灯箱一行；画面里没有灯箱的帧，标签文件留空（负样本）。

### 3.3 数据集

| 项目 | 数据 |
|---|---|
| 最终数据集 | 1086 张图 |
| 框数量 | 灯箱 1081，亮红灯 485，亮绿灯 511 |
| 划分（按整段视频） | 训练 742 张，验证 344 张；验证用 `105134`（红灯）、`112544`（红变绿）、`112926`（绿灯）三个没参与训练的视频 |
| 打包 | `light_dataset.zip`（约 80 MB）；`data.yaml` 没写 `path`，放到哪台电脑都能用 |

位置：`D:\VSCode\ros2技术集\智能车总文件\视觉模型\数据\数据集打包_给训练电脑用\light_dataset.zip`，标注好的完整数据在同级 `数据\标注_合并3类`。

脚本（在 `02_标注与数据集/`，**里面写的是当时的路径 `D:\light_ai\...`，要重新跑需要改路径**）：

| 脚本 | 作用 |
|---|---|
| `label.py` | 橙灯定位、灯箱框的初版标注 |
| `label2.py` | 模型灯箱框优先、亮红灯/亮绿灯标注、判断“拿不准”的帧 |
| `lamp.py` | 早期只标亮红灯的版本 |

| `export.py` | 早期只导出灯箱框标签 |

### 3.4 标注的局限（实话）

- 只抽查了约一百张叠加图，**没有逐张检查 1086 张**；第一轮橙灯定位的框有一部分偏了，后来改成模型框优先。
- **负样本很少**：画面里没有灯箱的图只有约 6 张。
- 几乎每帧都有一个灯在亮，**没有“三个灯全灭”**和橙灯亮的数据。
- 所有视频来自同一间教室、同一块灯箱。

## 4. 训练

### 4.1 早期试验：电脑 CPU 上的 YOLOv8n（只用来验证思路，模型已删除）

没有显卡，只能用 CPU，选最小的模型，开早停：

```python
from ultralytics import YOLO
m = YOLO("yolov8n.pt")
m.train(data="data.yaml", epochs=40, imgsz=640, batch=16, workers=4, device="cpu", patience=10, plots=False)
```

| 试验 | 数据 | 结果 |
|---|---|---|
| 单类（只有灯箱） | 359 张，视频 1、2 训练，视频 3 验证 | 20 轮，第 10 轮最好；mAP50 0.995，mAP50-95 0.912；约 42 ms/张 |
| 两类（灯箱 + 亮红灯） | 359 张 | 32 轮约 1 小时；mAP50-95 0.863（灯箱 0.892，亮红灯 0.834） |

这一步验证了“先框灯箱、再框框里的亮灯”的思路可行，也暴露了误检问题（见第 8 节）。网上找的现成红绿灯模型（Hugging Face 上的 8 类马路红绿灯、COCO 通用模型）训练的是马路红绿灯，对比赛的 LED 灯板不适用，没有采用。

### 4.2 YOLO11n（在另一台有显卡的 Linux 电脑上训练，用于电脑上验证）

把 `light_dataset.zip` 解压后，在解压出的 `light_dataset` 目录里运行：

```bash
pip install ultralytics
yolo detect train model=yolo11n.pt data=data.yaml epochs=100 imgsz=640 batch=16 patience=20
```

`args.yaml` 里记录的参数：`model yolo11n.pt`、`epochs 100`、`patience 20`、`batch 16`、`imgsz 640`、`device 0`。结果在 `runs/detect/train/weights/best.pt`。

结果（`03_训练/YOLO11n结果/`）：跑满 100 轮，第 86 轮最好：精确率 0.999，召回率 1.000，mAP50 0.995，mAP50-95 0.927。

### 4.3 YOLOv5n（上车用）

**为什么要用 YOLOv5n**：课程给小车的转换和推理脚本是按 **YOLOv5 v7.0** 写的，输出格式是 `[1, 25200, 5+类别数]`；YOLO11 的输出格式不同，课程的后处理不能直接用。

```bash
git clone https://github.com/ultralytics/yolov5
cd yolov5
git checkout v7.0
pip install -r requirements.txt
pip install onnx
```

数据配置（`03_训练/light.yaml`，把 `path` 改成你解压的位置）：

```yaml
path: /你解压的位置/light_dataset
train: images/train
val: images/val
names:
  0: light_box
  1: red_on
  2: green_on
```

训练：

```bash
python train.py --img 640 --batch 16 --epochs 100 --data light.yaml --weights yolov5n.pt
```

结果（`03_训练/YOLOv5n结果/`）：跑满 100 轮，**第 95 轮最好**：精确率 0.999，召回率 1.000，mAP50 0.995，mAP50-95 0.911（最后一轮第 99 轮是 0.905）。

> 说明：这里的命令是 v7.0 的标准写法。从 `opt.yaml` 看，实际训练用的数据文件叫 `data_v5.yaml`，权重参数是 `../trained_models/yolov5n/weights/last.pt`，目录下有 4 个 TensorBoard 事件文件——**推测训练是分几次运行或续训的**，这一点我没法确认。`batch 16`、`imgsz 640`、`epochs 100`、`device 0` 是确认的。

可能遇到的问题（**我没有验证过**）：新版 torch（2.6 起）加载旧版 YOLOv5 权重报 `weights_only` 错误，可设环境变量 `TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD=1`；YOLOv5 v7.0 较老，与 numpy 2 不兼容，装 `numpy<2`。

```bash
D:\light_ai\venv\Scripts\python.exe check_onnx.py ../06_模型文件/yolov5n_best.onnx
```

实测结果：opset 12；输入 `images [1,3,640,640]`；输出 `output0 [1,25200,8]`（8 = 4 个框坐标 + 1 个目标置信度 + 3 个类别）；12 种常规算子（`Add`、`Concat`、`Constant`、`Conv`、`MaxPool`、`Mul`、`Pow`、`Reshape`、`Resize`、`Sigmoid`、`Split`、`Transpose`）；onnxruntime 能正常推理。文件 SHA256 前 16 位 `288b43ff980a52b3`。

## 6. 转成小车用的 .om

昇腾板卡不能直接跑 ONNX，要用 CANN 的 `atc` 工具转成 `.om`。

| 问题 | 结论 |
|---|---|
| 为什么不在 Windows 电脑上转？ | CANN toolkit 只有 Linux 版 |
| 为什么没有在车上转？ | 课程记录板载转换约 2 小时，可能报错没结果；车上内存只有约 3.4 GB。**车上的 CANN 理论上能转，但我们没有试过** |
| 显卡有用吗？ | 没用，`atc` 编译算子只用 CPU |
| 在哪转？ | 你的 Linux 电脑，装 **CANN toolkit 7.0.RC1 的 x86_64 版**，版本必须和车上一致（车上 `version=7.0.RC1`，`innerversion=V100R001C13SPC005B246`），否则转出的 `.om` 在车上可能加载失败 |

转换命令（参数和课程 `common/util/atc.sh` 完全一致；`soc` 写**车上板卡的** `Ascend310B4`，不是电脑本身的型号；输入文件名要叫 `yolov5n.onnx`）：

```bash
source ~/Ascend/ascend-toolkit/set_env.sh
atc --model=yolov5n.onnx --framework=5 --output=yolov5n_bs1 --input_format=NCHW \
    --input_shape="images:1,3,640,640" --log=error --soc_version=Ascend310B4 \
    --input_fp16_nodes=images --output_type=FP16
```

详细步骤（装 CANN、常见问题）见 `04_转om/yolov5n转om_Linux电脑.md`。

### 6.1 检查转出来的 .om

拿到转好的 `onnx.zip`（里面是 `yolov5n.onnx` 和 `yolov5n_bs1.om`），做了三项检查：

| 检查 | 结果 |
|---|---|
| ONNX 的哈希 | 和我们验证过的 `best.onnx` **完全相同** |
| `.om` 文件头里嵌的转换命令（`04_转om/check_om.py`） | `--soc_version=Ascend310B4`、`--input_shape=images:1,3,640,640`、`--input_fp16_nodes=images`、`--output_type=FP16` **全部符合**；使用的是 7.0.RC1 的 x86_64 `atc` |
| 文件 | `yolov5n_bs1.om`，4,501,008 字节，文件头魔数 `IMOD` |

```bash

```

## 7. 验证

### 7.1 电脑上：验证集对比（最重要的一项）

`05_验证/verify_val.py` 复用 `light_infer.py` 的识别和判断逻辑，在验证集上跑模型，和标签推出的真实状态对比（真实状态：有 class 1 → red，有 class 2 → green，只有 class 0 → off，没有框 → none）。

```bash
cd 05_验证
D:\light_ai\venv\Scripts\python.exe verify_val.py --model ../06_模型文件/yolov5n_best.onnx
```

**实测结果**：共 344 张，错误 0 张；真实 green → 判断 green：172；真实 red → 判断 red：172；**红判绿（最危险）：0**。这条命令也能跑 `.om`（在小车上，先 `source` CANN 环境，用 `--images`、`--labels` 指定图片和标签目录）。

> 判断逻辑：灯箱框先过几何过滤（长宽比 2.5 到 4.5，框中心高度在画面的 20% 到 85%）；亮灯框的中心必须落在通过过滤的灯箱框里才算“该灯亮”；再按亮的灯给出 `red` / `green` / `conflict`（红绿同时）/ `off`（有灯箱没亮灯）/ `none`（没灯箱）；连续 3 帧一致才切换状态；**只有 `green` 才放行**。

### 7.2 电脑摄像头试验（发现了问题）

`05_验证/light_yolo11_cam.py` 用 YOLO11n 的 `.pt` 在笔记本摄像头上实时试：

```bash
D:\light_ai\venv\Scripts\python.exe light_yolo11_cam.py --model ../06_模型文件/yolo11n_best.pt
```

画面里灯箱、亮红灯、亮绿灯会画框，左上角显示状态和 `GO`/`STOP`，被过滤的框画成灰色并写出原因，低于阈值的检测也会画出来（暗灰细框），方便调阈值。

试验中的发现：

- **椅子、人被框成灯箱**：训练里没有负样本。
- **红灯亮时灯箱框没出来**：灯没亮时灯箱分数就只有 0.57，红灯一亮光晕把分数拉到阈值以下，“亮灯框必须在灯箱里”的规则又把真红灯否掉。降低 `--conf-box` 可以缓解。
- **笔记本摄像头和小车摄像头不同**：训练图是小车摄像头拍的，在笔记本上测的结果不能代表车上。
- 这些都指向同一件事：**需要补拍负样本和更多样的数据**（见第 11 节）。

### 7.4 小车压力太大之后：电脑识别

车上识别让小车压力很大，所以又做了“小车传图、电脑识别、结果传回小车”的方案，文件和运行指令在同级文件夹 `yolov5n电脑分布式通信/`。在电脑上用回环地址加录好的视频测通了：状态随画面变化（none → red → green），往返延迟约 45 到 60 ms，电脑断开后小车端立即变 `stale`；**在小车上的实际运行没有验证**。

## 8. 遇到的问题与解答

| 问题 | 原因 | 处理 |
|---|---|---|
| 车上 `record.py` 录不了视频 | 它订阅 `/camera1/image_raw`，车上这个话题没有在发布 | 自己写 `record_video.py`，直接读 USB 摄像头 |
| 抽帧时 OpenCV 读不到图 | `cv2.imread` 不支持含中文的路径 | 用 `cv2.imdecode(np.fromfile(...))` |
| 导入 torch 很慢，窗口像卡住 | 第一次导入要编译缓存、杀毒扫描 | 等 1 到 2 分钟，不要按 `Ctrl+C` |
| 椅子、人被框成灯箱 | 训练里没有负样本 | 先用几何过滤和更高置信度；根本办法是补负样本重训 |
| 绿灯认不出来 | 最早的数据里没有绿灯 | 补拍绿灯、红变绿的视频，重新标注训练 |
| 灯箱被切在画面边缘，标成“灯没亮” | 灯可能只露出一半 | 标注时剔除这类帧 |
| 画面里有亮灯但没框到灯箱，被当成负样本 | 自动标注没找到灯箱 | 加规则：有亮灯却没有灯箱框的帧一律剔除 |
| 橙灯定位的灯箱框偏了 | 只框到橙灯附近，或框到红锥桶上 | 改成训练好的灯箱模型的框优先，橙灯定位作后备 |
| YOLO11 模型不能上车 | 课程的转换和推理按 YOLOv5 v7.0 写，输出格式不同 | 用原版 YOLOv5 v7.0 训练 YOLOv5n |
| 导出的 ONNX 可能转不了 | v7.0 默认 opset 17 | 导出时写 `--opset 12`，不要 `--dynamic` |
| 在车上转 `.om` 慢且可能失败 | 课程记录约 2 小时、可能报错；车上内存只有约 3.4 GB | 在 Linux 电脑上用 CANN 7.0.RC1 x86_64 转，`soc` 写 `Ascend310B4` |
| 车上 conda 的 `python3` 导入不了 `rclpy` | `rclpy` 是系统 Python 3.10 的扩展 | ROS 相关脚本用 `/usr/bin/python3`；识别用 conda 的 `python3` |
| 车上不能 `pip install` | 小车不能访问外网 | 在电脑下载好再 `scp` |
| 小车压力太大，没法同时跑行驶程序 | NPU 推理、torch 导入和 CPU 上的 NMS，加上车上还启动了 rviz2（**推断，没量过**） | 改成电脑识别（7.4） |

## 11. 没验证的事项与下一步

**下一步（建议）**

1. 在车上对着红灯、绿灯、没灯、人和椅子实测，看状态是否判对，**红判绿必须为 0**；记录帧率、`free -h`、`npu-smi info`。
2. **补拍数据**：灯全灭、不同距离、角度、光线、室外，以及 100 到 200 张没有灯箱的画面（椅子、人、桌子、锥桶、深色衣服、屏幕，标签文件留空）。先确认灯箱能不能手动亮绿灯、橙灯，不能就拍倒计时结束亮绿灯的完整过程。
3. 补拍后重新标注（自动标注脚本要先确认在新画面上还能定位灯箱）、重训 YOLOv5n、重新导出和转 `.om`，再用 `verify_val.py` 验证。
4. 现场标定停车阈值，并在 `pure_track_test` 里加红灯停、绿灯走的状态机（只有确认绿灯才放行）。
